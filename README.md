# MASTER PROMPT — ВЕБ-ПРИЛОЖЕНИЕ ДЛЯ ТЕСТИРОВАНИЯ

## 1. РОЛЬ

Ты работаешь как senior full-stack/frontend-разработчик, архитектор программного обеспечения и UI/UX-инженер.

Твоя задача — разработать качественное, поддерживаемое веб-приложение для создания и прохождения тестов.

Не пытайся реализовать всё приложение за один шаг.

Работай поэтапно. Перед каждым крупным этапом анализируй текущий код проекта, проверяй существующую архитектуру и только после этого вноси изменения.

Главный приоритет:

1. Корректность бизнес-логики.
2. Надёжная архитектура.
3. Типобезопасность.
4. Простота поддержки.
5. Хороший UX.
6. Производительность.
7. Визуальная привлекательность.

Не жертвуй архитектурой ради скорости написания кода.

# 2. ЦЕЛЬ ПРИЛОЖЕНИЯ

Создать веб-приложение для создания, импорта, экспорта и прохождения тестов.

Приложение должно позволять:

* создавать тесты;
* создавать вопросы;
* редактировать вопросы;
* удалять вопросы;
* менять порядок вопросов;
* импортировать тесты из JSON;
* экспортировать тесты в JSON;
* проходить тесты;
* проходить тесты в режиме "Практика";
* проходить тесты в режиме "Экзамен";
* переключаться между вопросами;
* возвращаться к предыдущим вопросам;
* сохранять прогресс;
* загружать сохранённый прогресс;
* досрочно завершать тестирование;
* просматривать статистику;
* сбрасывать прохождение;
* работать с несколькими типами вопросов;
* отображать обучение, если вопросы отсутствуют.

Приложение должно работать в первую очередь как клиентское веб-приложение без обязательного backend.

Архитектура должна позволять в будущем подключить backend/API без полной переделки приложения.

# 7. ТИПЫ ВОПРОСОВ

Поддерживаются четыре типа вопросов:

```text
single
multiple
text
order
```

Используй discriminated union.

Пример концепции:

```ts
type Question =
  | SingleChoiceQuestion
  | MultipleChoiceQuestion
  | TextQuestion
  | OrderQuestion;
```

Не используй один огромный интерфейс с десятками необязательных полей, если discriminated union позволяет сделать модель надёжнее.

---

# 8. SINGLE — ОДИНОЧНЫЙ ОТВЕТ

Пользователь может выбрать только один вариант.

Пример:

```text
Вопрос:
Какой язык используется для разработки конфигураций 1С?

○ JavaScript
○ Python
● 1С
○ C#
```

Правильный ответ — один вариант.

В модели:

```text
correctAnswer: ["option-id"]
```

Требования:

* нельзя выбрать несколько вариантов;
* при выборе другого варианта предыдущий автоматически снимается;
* можно изменить ответ;
* ответ может быть пустым.

---

# 9. MULTIPLE — МНОЖЕСТВЕННЫЙ ОТВЕТ

Пользователь может выбрать несколько вариантов.

Например:

```text
Какие технологии являются языками программирования?

☑ Python
☑ JavaScript
☐ HTML
☐ CSS
```

Правильный ответ может содержать несколько вариантов.

По умолчанию ответ считается правильным только при полном совпадении множества выбранных и правильных вариантов.

Например:

```text
Правильные: A, C, D
Пользователь: A, C
```

Результат:

```text
Неправильно
```

Также:

```text
Правильные: A, C, D
Пользователь: D, C, A
```

Результат:

```text
Правильно
```

Порядок выбранных вариантов не должен иметь значения.

---

# 10. TEXT — РУЧНОЙ ВВОД

Пользователь вводит ответ вручную.

Один вопрос может иметь несколько допустимых вариантов правильного ответа.

Например:

```text
Вопрос:
Столица России?

Ответ:
Москва
```

Правильные варианты:

```text
Москва
москва
г. Москва
Moscow
```

При проверке по умолчанию:

1. удалить пробелы в начале и конце;
2. привести к нижнему регистру;
3. сравнить с каждым допустимым вариантом.

Если совпал хотя бы один допустимый вариант — ответ правильный.

Архитектуру сделай расширяемой для будущего добавления:

* чувствительности к регистру;
* частичного совпадения;
* регулярных выражений;
* нормализации пунктуации.

Но в первой версии реализуй только базовую нормализацию.

---

# 11. ORDER — ПОРЯДОК

Пользователь должен расположить элементы в правильном порядке.

Например:

```text
Расположите этапы в правильном порядке:

[ Создание ]
[ Проверка ]
[ Публикация ]
[ Тестирование ]
```

Правильный порядок:

```text
Создание
Тестирование
Проверка
Публикация
```

Проверка выполняется сравнением последовательности ID.

Текст элементов не должен использоваться как идентификатор.

Пользователь должен иметь возможность:

* перетаскивать элементы;
* либо использовать кнопки вверх/вниз;
* видеть текущий порядок.

Если drag-and-drop требует дополнительной библиотеки, сначала оцени, можно ли реализовать это без неё.

---

# 12. ОБЩАЯ МОДЕЛЬ ВАРИАНТОВ

Для вариантов ответа используй стабильный `id`.

Например:

```ts
interface AnswerOption {
  id: string;
  text: string;
}
```

Никогда не используй индекс массива как постоянный идентификатор.

Это важно для:

* перемешивания;
* изменения порядка;
* сохранения;
* импорта/экспорта;
* статистики.

---

# 13. ПРАВИЛА ПРОВЕРКИ ОТВЕТОВ

Создай отдельный модуль:

```text
answer-checker.ts
```

Он не должен зависеть от React.

Он должен предоставлять функции примерно такого уровня:

```ts
checkAnswer(question, userAnswer): AnswerResult
```

Результат должен быть типизирован.

Например:

```ts
interface AnswerResult {
  isCorrect: boolean;
  isAnswered: boolean;
}
```

При необходимости расширь результат.

Обязательно напиши unit-тесты для всех типов вопросов.

---

# 14. РЕЖИМЫ ТЕСТИРОВАНИЯ

Существует два режима:

```text
practice
exam
```

Используй enum или union type.

---

# 15. РЕЖИМ "ПРАКТИКА"

В режиме практики пользователь отвечает на вопрос.

После проверки ответа пользователь должен увидеть:

* правильный/неправильный результат;
* правильный ответ;
* пояснение к вопросу, если оно есть.

Пример:

```text
✓ Правильно

Правильный ответ:
...

Пояснение:
...
```

Если ответ неправильный:

```text
✗ Неправильно

Правильный ответ:
...

Пояснение:
...
```

Пользователь должен иметь возможность перейти дальше.

---

# 16. РЕЖИМ "ЭКЗАМЕН"

В экзамене пользователь не должен получать информацию о правильности ответа до завершения теста.

До окончания экзамена запрещено показывать:

* правильный ответ;
* неправильный ответ;
* пояснение;
* процент правильных;
* любую другую информацию, позволяющую определить правильность ответа.

После выбора ответа можно показать только:

```text
Ответ сохранён
```

или аналогичную нейтральную информацию.

После завершения теста показать результаты.

---

# 17. СОСТОЯНИЕ ПРОХОЖДЕНИЯ

Не смешивай Test и QuizAttempt.

Создай отдельную сущность:

```ts
interface QuizAttempt {
  id: string;
  testId: string;
  mode: "practice" | "exam";
  currentQuestionIndex: number;
  answers: UserAnswer[];
  startedAt: string;
  updatedAt: string;
  finishedAt?: string;
  status: "in-progress" | "completed";
}
```

Это пример.

При необходимости расширь модель.

---

# 18. ОТВЕТ ПОЛЬЗОВАТЕЛЯ

Ответ пользователя должен быть отдельной сущностью.

Не изменяй `Question.correctAnswer` во время прохождения.

Правильный ответ и ответ пользователя должны храниться отдельно.

Например:

```ts
interface UserAnswer {
  questionId: string;
  value: unknown;
}
```

Но постарайся сделать типобезопасную модель вместо бездумного использования `unknown`.

---

# 19. НАВИГАЦИЯ ПО ВОПРОСАМ

Во время прохождения пользователь должен иметь возможность:

* перейти к следующему вопросу;
* перейти к предыдущему;
* открыть любой вопрос;
* видеть номер текущего вопроса;
* видеть отвеченные вопросы;
* видеть вопросы без ответа.

Например:

```text
1 ✓
2 ✓
3 —
4 ✓
5 —
6 ✓
```

Где:

```text
✓ — есть ответ
— — нет ответа
● — текущий вопрос
```

Не показывай правильность ответа в экзамене.

---

# 20. ДОСРОЧНОЕ ЗАВЕРШЕНИЕ

Пользователь должен иметь возможность завершить тестирование досрочно.

Перед завершением показать подтверждение:

```text
Вы уверены, что хотите завершить тест?

Без ответа:
3

После завершения изменить ответы будет нельзя.
```

После подтверждения:

```text
QuizAttempt.status = completed
```

и открыть страницу результатов.

---

# 21. ЗАВЕРШЕНИЕ ПОСЛЕ ПОСЛЕДНЕГО ВОПРОСА

После последнего вопроса не завершай экзамен автоматически без возможности подтверждения.

Покажи:

```text
Тест завершён

Отвечено: 20 из 20

Завершить тест?
```

Для практики можно использовать более простой UX.

---

# 22. СТАТИСТИКА

После завершения показать:

* общий процент;
* количество правильных;
* количество неправильных;
* количество без ответа;
* количество вопросов;
* время прохождения;
* статистику по типам вопросов.

Например:

```text

17 правильных

1 без ответа
```

Также показать список вопросов:

```text
1. ✓

3. ✗
4. —
5. ✓
```

При открытии вопроса показать:

* вопрос;
* ответ пользователя;
* правильный ответ;
* пояснение.

```text
Варианты ответа
Правильные варианты

```

# 27. ФОРМА TEXT


# 28. ФОРМА ORDER

---

# 29. ВАЛИДАЦИЯ ВОПРОСОВ

Нельзя сохранить некорректный вопрос.

Проверь:

Общие:

* есть текст;
* есть ID;
* корректный тип.

Single:

* минимум 2 варианта;
* выбран ровно один правильный вариант.

Multiple:

* минимум 2 варианта;
* выбран хотя бы один правильный вариант.

Text:

* есть хотя бы один правильный вариант.

Order:

* есть минимум 2 элемента;
* нет повторяющихся ID.

Ошибки должны отображаться пользователю понятно.

---

# 30. JSON ИМПОРТ

Приложение должно уметь импортировать тест из JSON.

При импорте:

1. прочитать файл;
2. распарсить JSON;
3. проверить структуру;
4. проверить version;
5. проверить вопросы;
6. проверить типы;
7. проверить ID;
8. проверить правильные ответы;
9. показать понятную ошибку при проблеме;
10. только после успешной валидации добавить тест.

Никогда не доверяй импортируемому JSON.

---

# 31. JSON ЭКСПОРТ

Пользователь должен иметь возможность скачать тест в JSON.

JSON должен быть стабильным и человекочитаемым.

Используй:

```text
version
```

чтобы в будущем можно было менять формат.

Не включай во внешний JSON лишнее внутреннее состояние UI.

---

# 32. СОХРАНЕНИЯ

Разделяй:

```text
Test JSON
```

и:

```text
Attempt Save JSON
```

Это разные сущности.

Test JSON содержит:

* тест;
* вопросы;
* правильные ответы.

Attempt Save JSON содержит:

* ID теста;
* режим;
* ответы пользователя;
* текущий вопрос;
* время;
* состояние прохождения.

---

# 33. ЛОКАЛЬНОЕ ХРАНИЛИЩЕ

На первом этапе используй локальное хранение.

Можно использовать:

```text
localStorage
```

Если данных станет много — архитектура должна позволять заменить persistence layer на IndexedDB.

Не привязывай бизнес-логику непосредственно к localStorage.

Сделай абстракцию:

```text
persistence service
```

Например:

```ts
saveAttempt(...)
loadAttempt(...)
deleteAttempt(...)
listAttempts(...)
```

---

# 34. АВТОСОХРАНЕНИЕ

Прогресс прохождения должен автоматически сохраняться.

Минимум:

* при изменении ответа;
* при переходе между вопросами;
* при закрытии/обновлении страницы, если возможно.

При повторном открытии приложения пользователь должен иметь возможность продолжить незавершённое прохождение.

---

# 35. СБРОС

Пользователь должен иметь возможность:

```text
Сбросить прохождение
```

Перед сбросом показать подтверждение.

После сброса:

* удалить ответы;
* удалить прогресс;
* создать новое состояние прохождения либо вернуть пользователя к выбору режима.

---

# 36. ПУСТОЕ СОСТОЯНИЕ

```text
loading
empty
error
success
disabled
selected
current
answered
unanswered
completed
```

# 39. ТЕМНАЯ ТЕМА

# 40. ДОСТУПНОСТЬ

# 41. ОБРАБОТКА ОШИБОК

Ошибки должны быть понятны пользователю.

Не показывай технические stack trace обычному пользователю.

Например, вместо:

```text
SyntaxError: Unexpected token...
```

показывай:

```text
Не удалось импортировать файл.

JSON содержит ошибку или имеет неподдерживаемую структуру.
```

Но техническую информацию оставляй доступной в dev console.

---

# 42. ТЕСТИРОВАНИЕ

Обязательно напиши unit-тесты для domain/business logic.

Минимальный набор:

## Single

* правильный ответ;
* неправильный ответ;
* отсутствие ответа.

## Multiple

* полный правильный набор;
* неполный набор;
* лишний вариант;
* правильный набор в другом порядке;
* пустой ответ.

## Text

* точное совпадение;
* различный регистр;
* пробелы;
* альтернативный правильный ответ;
* неправильный ответ;
* пустой ответ.

## Order

* правильный порядок;
* неправильный порядок;
* пустой ответ;
* частично изменённый порядок.

## Statistics

Проверь:

* правильные;
* неправильные;
* без ответа;
* процент;
* разные типы вопросов.

## Persistence

Проверь:

* сохранение;
* загрузку;
* удаление;
* восстановление.

## JSON

Проверь:

* корректный JSON;
* повреждённый JSON;
* неизвестный тип вопроса;
* отсутствующие поля;
* дублирующиеся ID;
* некорректные правильные ответы;
* неподдерживаемую version.

---

# 43. ВАЖНОЕ ПРАВИЛО ПРО БИЗНЕС-ЛОГИКУ

Не дублируй правила проверки ответа в нескольких местах.

Нельзя:

```text
PracticeQuestion.tsx → своя проверка
ExamPage.tsx → своя проверка
Statistics.tsx → третья проверка
```

Должен существовать единый источник истины:

```text
answer-checker.ts
```

То же самое касается расчёта статистики.

---

# 44. ВАЖНОЕ ПРАВИЛО ПРО EXAM

В режиме экзамена UI не должен получать информацию о правильности текущего ответа до завершения.

Архитектуру проектируй так, чтобы случайно не показать правильный ответ.

После завершения можно выполнить полную проверку всех ответов и сформировать результат.

---

# 45. ПЕРЕМЕШИВАНИЕ

Сделай архитектуру расширяемой для:

* перемешивания вопросов;
* перемешивания вариантов.

Но если это не входит в первую реализацию, не добавляй функциональность без необходимости.

Если реализуешь перемешивание, обязательно сохраняй фактический порядок прохождения в QuizAttempt.

Иначе после перезагрузки порядок может измениться.

---

# 46. ИДЕНТИФИКАТОРЫ

Все сущности должны иметь стабильные ID.

Не используй:

```text
array index
```

как постоянный ID.

ID должны использоваться для:

* вопросов;
* вариантов;
* тестов;
* попыток.

---

# 47. ВЕРСИОНИРОВАНИЕ JSON

Все экспортируемые форматы должны содержать:

```json
{
  "version": 1
}
```

В будущем должна существовать возможность сделать миграцию:

```text
version 1 → version 2
```

Не ломай старые сохранения без необходимости.

---

# 48. БЕЗОПАСНОСТЬ

Не выполняй импортированный текст как код.

Никогда не используй:

```text
eval
new Function
dangerouslySetInnerHTML
```

без крайней необходимости.

Импортируемый JSON рассматривай как недоверенные данные.

---

# 49. НЕ ПЕРЕУСЛОЖНЯЙ

Не добавляй без необходимости:

* backend;
* авторизацию;
* базу данных;
* WebSocket;
* Redux;
* сложный state machine;
* микросервисную архитектуру;
* Docker;
* CI/CD.

Первая версия должна быть локальным качественным веб-приложением.

Архитектура должна позволять добавить их позже.

```text
disable lint
ignore TypeScript error
```
